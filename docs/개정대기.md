## 13. 2026-11-08 P7-0: F-11 '페이지 안 찾기' 초안: 결정됨 → D-59, 기능정의 F-11 반영함 (2026-11-08)

D-56으로 Ctrl+F는 앱이 받는다(지금은 검색 창 S-05). 이어서 만드는 막대의 범위·완료 기준 초안이다. 아래 "사용자가 정할 것"이 정해지면 기능정의 F-11로 옮기고 D 번호를 쓴다. 화면(위치·겹침·문구)은 NOTE-design 화면설계 S-14(자리: 도구 막대 바로 아래 한 줄, design 11-08).

### 확인한 사실 (2026-11-08 main 78611b9)
- 페이지 제목은 편집기 밖의 `<textarea class="page-title">`이다(`src/app/PageView.tsx` 32행). ProseMirror 꾸밈(decoration)은 편집기 문서 안에만 그릴 수 있어, 제목 칸 안의 일치 여러 개를 강조할 수 없다(입력칸은 선택 하나만 보일 수 있음).
- 꾸밈은 이미 쓰고 있다(`src/editor/placeholder.ts`, `src/editor/uploadPlaceholder.ts`, `@tiptap/pm/view`). `@tiptap/pm`은 직접 의존성이다(`package.json` 22행). 새 라이브러리가 필요 없다.
- 검색 창에서 결과를 고르면 페이지를 열고 편집기에 포커스만 준다. 첫 일치 위치로 스크롤·강조는 아직 없다(`src/app/AppShell.tsx` 687행 주석 "편집기 쪽 기능이 생기면 query로 붙인다"). `onOpenPage(pageId, query)`로 검색어는 이미 넘어온다(`SearchPanel.tsx` 13·93행). 그래서 F-04 완료 기준 "첫 일치 위치로 스크롤"과 화면설계 S-05 "1.5초 옅게 강조"는 아직 채워지지 않았다.
- 검색 창·AI 패널·제목 칸은 Enter를 `isComposing`일 때 넘긴다(한글 조합 중 Enter는 입력기 몫). 같은 규칙을 쓴다.
- 코드 블록 30개·5만 자 페이지에서 코드 안 입력 p50 50ms로 NF-04를 이미 넘는다(lowlight 전체 재강조, 진행현황 다음 판 후보). 찾기 강조가 이 비용에 더해지지 않아야 한다.

### 초안: F-11 페이지 안 찾기
- 설명: 지금 열린 페이지 본문에서 낱말을 찾아 일치를 모두 강조하고, 하나씩 옮겨 다닌다. 앱이 직접 그리는 막대이고 WebView2 기본 찾기 막대는 쓰지 않는다(D-56).
- 열기
  - 페이지 화면(제목 칸·본문·AI 패널 포함)에서 Ctrl+F. 휴지통·설정·빈 상태에서는 지금처럼 검색 창(S-05)을 연다. 대화상자·메뉴·검색 창이 떠 있으면 열지 않는다(WebView2 찾기 막대도 열리지 않는다).
  - 본문에 한 줄·200자 이하 선택이 있으면 그 글로 찾는 말을 채우고, 아니면 지난 찾는 말을 전체 선택한 채로 둔다(design 안).
  - 막대가 열린 채 Ctrl+F를 누르면 입력칸으로 가서 전체 선택한다.
- 찾는 범위(추천)
  - 본문의 모든 글: 문단·제목·목록·체크리스트·인용·표 칸·코드 블록. 페이지 제목은 넣지 않는다(사용자가 정할 것 ②).
  - 한 블록(textblock) 안에서만 맞춘다. 굵게·링크 같은 서식 경계를 걸친 일치는 찾는다. 두 블록에 걸친 일치는 찾지 않는다.
  - 대소문자 구별 없음(F-04 검색과 같음), 유니코드 NFC로 맞춰 비교, 띄어쓰기는 그대로. 정규식·낱말 단위·대소문자 켜기 옵션은 없다.
  - 1글자부터 찾는다.
- 표시
  - 모든 일치를 `--color-mark`로, 지금 일치는 한 단계 진하게(모양은 design). 막대에 `n/m`(일치 없으면 `0/0`과 "일치 없음"). 1,000개를 넘으면 `n/1,000+`로 보이고 강조도 앞 1,000개까지만 그린다(design 안).
  - 처음 열거나 찾는 말을 바꾸면 커서 위치 다음의 첫 일치가 지금 일치다. 지금 일치는 도구 막대·찾기 막대에 가리지 않게 보이는 자리로 바로 스크롤한다(부드러운 스크롤 없음, F-10과 같음).
- 이동: 입력칸에서 Enter 다음·Shift+Enter 이전(한글 조합 중 Enter는 입력기 몫). 페이지 화면 어디서나 F3·Ctrl+G 다음, Shift+F3·Ctrl+Shift+G 이전. 막대가 닫혀 있으면 이 키들은 지난 찾는 말로 막대를 열고 그 방향으로 옮긴다(지난 말이 없으면 빈 막대만 연다). 끝에서 처음으로, 처음에서 끝으로 돌아간다(design 안).
- 닫기: Esc(입력칸에서) 또는 닫기 버튼. 강조를 모두 지우고 편집기로 포커스를 돌린다. 지금 일치가 있으면 그 글을 선택한 채로, 없으면 열기 전 커서 자리로(design 안). 페이지를 바꾸면 막대는 열린 채 새 페이지에서 같은 말로 다시 찾는다.
- 한글 조합
  - 찾기 입력칸: 조합 중인 글자까지 넣어 찾는다(추천, 사용자가 정할 것 ③). 입력이 멈추고 100ms 뒤 다시 찾는다.
  - 본문(막대가 열린 채 편집할 때): 편집기가 조합 중(`view.composing`)이면 일치를 다시 세지 않고 조합이 끝난 뒤 다시 센다. 조합 중 꾸밈을 바꾸면 입력기 글자가 깨질 수 있어서다.
  - 막대를 닫은 직후 본문에 한글을 치면 첫 글자부터 조합 중 글자가 보인다(D-56 버그가 다시 나지 않음).
- 문서가 바뀔 때: 거래(transaction)마다 기존 강조를 문서 변경에 맞춰 옮기고(`DecorationSet.map`), 입력이 멈추고 100ms 뒤 바뀐 문서로 다시 센다. 강조는 꾸밈이라 문서를 바꾸지 않는다: 자동 저장·실행 취소 기록이 생기지 않고, 본문 JSON·내보내기·AI·검색 색인에 들어가지 않는다.
- 범위 밖: 바꾸기·모두 바꾸기(추천, 사용자가 정할 것 ④), 여러 페이지에 걸친 찾기(검색 창 F-04 몫), 제목 칸 안 강조.
- 완료 기준
  - 위 열기·이동·닫기·개수 동작이 모두 된다. Ctrl+F·F3·Shift+F3·Ctrl+G·Ctrl+Shift+G 어느 것도, 어느 화면에서도 WebView2 기본 찾기 막대를 열지 않는다(WebView2가 이 키들로 찾기 막대를 연다는 것은 design 확인, 구현이 다시 확인한다). 페이지가 아닌 화면에서 F3·Ctrl+G 계열은 아무것도 하지 않는다.
  - 막대를 닫고 본문에 한글을 바로 치면 조합 중 글자가 보인다(Alt+Tab 없이).
  - 성능(NF-04): 5만 자 페이지(코드 블록 30개 시험 페이지 포함)에서 다시 찾기 한 번 50ms 이하. 막대를 연 채 본문 타이핑 지연이 막대를 닫았을 때와 같은 기준(p95 50ms·최대 100ms)을 지킨다. 코드 블록 안 입력은 이미 넘는 문제(lowlight)라 막대를 열어 더 느려지지 않는지만 본다.
  - 강조가 실행 취소 기록·자동 저장을 만들지 않는다(Ctrl+Z 한 번이 찾기 전 편집을 되돌림).
