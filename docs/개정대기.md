## 4. (c) 사용자 결정 — 카드 4장, 질문 16개

계약-AI 10절과 겹치는 것은 하나로 합쳤다(8 ↔ ⑥, 7 ↔ ⑫). 진행현황 "재개 때 사용자 결정"의 항목도 넣었다.

### 카드 1. 저장 구조·계약 변경 (계약-DB v2)

**1-① 첨부·페이지 id 재사용 막기** (진행현황)
- 배경: 계약-DB v1은 `INTEGER PRIMARY KEY`(AUTOINCREMENT 없음)라 마지막 행을 지우면 그 번호가 다시 쓰일 수 있다. 첨부 파일 이름이 `<id>.<확장자>`라서, 지운 이미지 번호가 새 이미지에 다시 쓰이면 그 번호를 가리키던 노드(실행 취소로 되살린 이미지, 내보낸 파일)가 다른 이미지를 보일 수 있다.
- A(추천) 스키마 v1에 `AUTOINCREMENT`를 붙인다. 대가: SQLite가 `sqlite_sequence` 표를 하나 더 쓴다(성능 차이는 이 규모에서 무시할 수준). 아직 사용자 데이터가 없어 지금 바꾸는 비용이 가장 작다.
- B `app_state`에 다음 번호 카운터를 둔다. 대가: 번호를 매기는 코드를 직접 써야 하고 트랜잭션 안에서 함께 갱신해야 한다.
- C 그대로 둔다. 대가: 위 오표시 위험이 남는다.

**1-② 스키마 v2 범위: AI 표 + 휴지통 원래 위치** (계약-AI ⑫ + 진행현황 TrashItem)
- 배경: AI 전송 제외·사용 기록·하루 상한(테스트 7)을 담을 곳이 계약 v1에 없다. 화면설계 S-04는 휴지통 항목의 원래 위치를 보이는데 `TrashItem`은 `{id,title,trashedAt,descendantCount}`뿐이다.
- A(추천) 계약-DB v2를 한 번에: `pages.ai_exclude`, `ai_usage` 표, `app_state` 키(`ai_daily_limit`·`api_key_last4`), 오류 kind 추가, `TrashItem`에 `parentId`·원래 경로(조회 때 계산) 추가. 대가: 계약-DB·계약-AI·db-types를 함께 고치고 backend1·backend2·frontend1이 맞춰야 한다.
- B AI 쪽만 v2, `TrashItem`은 그대로 두고 S-04에서 원래 위치 표시를 뺀다. 대가: 휴지통에서 같은 이름 페이지를 구별하기 어렵다.
- C 전송 제외를 별도 표(`ai_excluded_pages`)로. 대가: 조회 때 조인이 하나 더 들고 계약-AI 3.1을 다시 써야 한다.

**1-③ 창 닫기 때 저장이 실패하면** (진행현황)
- 배경: 지금 구현은 저장을 3초 기다린 뒤 결과와 상관없이 닫는다(`CLOSE_SAVE_TIMEOUT_MS = 3000`, 현재 꺼 둠). 닫히면 메모리에 있던 저장 못 한 내용은 사라진다.
- A(추천) 저장이 실패하거나 3초 안에 끝나지 않으면 닫지 않고 "저장하지 못한 내용이 있습니다 [다시 저장] [그래도 닫기]"를 묻는다. 대가: 디스크 문제가 계속되면 사용자가 한 번 더 눌러야 닫힌다. 코드가 조금 는다.
- B 지금처럼 3초 뒤 닫는다. 대가: 디스크 가득 참 같은 때 마지막 입력을 말없이 잃는다(F-05 "닫기 전에 저장"을 지키지 못한 것을 알리지 않음).

**1-④ 화면 상태를 어디에 저장하나** (테스트 7·27)
