- 확정된 결정은 D-nn으로 남긴다. 뒤집을 때는 기존 항목을 고치지 않고 새 ID를 쓴다. 문구만 보완할 때는 결정 칸 끝에 `(YYYY-MM-DD 보완: …)`로 적는다.

### D-04 오프라인 우선 데스크탑 앱

- 결정: Windows PC에서 돌아가는 데스크탑 앱으로 만든다. 데이터는 로컬에 저장하고, AI를 뺀 모든 기능이 인터넷 연결 없이 동작한다. 웹·모바일판은 만들지 않는다.
- 근거: 아이디어 노트 1절 "오프라인에서는 편집만 정상 동작한다", 6절 "저장소: 로컬 우선". 사용자 목표(2026-10-26): "우선 오프라인에서 사용 가능한 데스크탑 앱으로 만드는 게 목표."
- 대안: 웹 앱·클라우드 동기화 방식. 모바일 동기화는 4절 제외 목록에 있다.
- 관련: NF-01, NF-06, D-06, D-07

### D-05 AI는 Claude API를 쓰는 부가 기능, 비용은 Max 플랜 월간 API 크레딧
- 결정일: 2026-10-25 (아이디어 노트 2절·5절)
- 결정: AI 어시스트는 Claude API로 만든다. 비용은 Claude Max 플랜에 포함된 월간 API 크레딧으로 충당한다. AI는 부가 기능이며, 앱의 기본 동작은 AI 없이 완결된다. 모델은 가벼운 작업에 `claude-haiku-5-5`, 긴 노트 분석·글쓰기에 `claude-sonnet-5-5`를 쓴다.
- 근거: 아이디어 노트 2절(Claude API, Max 플랜 크레딧)과 5절(모델 선택, 동작 원칙).
- 참고(아이디어 노트 2절의 사실): 크레딧을 받으려면 Claude Console 조직을 플랜에 연결해야 하고, 연결한 조직은 나중에 직접 바꿀 수 없다. 이 크레딧은 Claude 앱·Claude Code 사용 한도와 별개다. 소진되면 다음 월간 지급 때까지 API 요청이 멈춘다. 금액·만료일은 Console의 Billing > Promotional credits에서 확인한다.
- 대안: 로컬 LLM, 다른 회사 API, 종량 결제. 아이디어 노트에서 검토하지 않았다.
- 관련: F-08, NF-05, D-09

### D-06 저장 방식: SQLite만 사용
- 결정일: 2026-10-26 (사용자 결정, 카드 20261026-0014-NOTE-pm-p0-tech)
- 결정: 페이지 트리·본문·설정·AI 사용 기록을 로컬 SQLite 파일 하나에 저장한다. 본문은 TipTap JSON으로 저장한다. 이미지는 데이터 폴더의 첨부 폴더에 파일로 둔다. 이식성은 마크다운 내보내기(F-06)로 확보한다.
- 근거: SQLite는 전문 검색 색인(FTS5)·트리 순서·후순위 DB 뷰(F-20)에 유리하고 트랜잭션으로 원자적 저장이 쉽다. 사용자 1명이 앱 안에서만 편집하므로(D-03) 마크다운 원본의 외부 편집기 호환 이득이 작다. 병행보다 동기화 코드가 적다.
- 대안: 마크다운 파일만(이식성 최고, 검색·트리 순서·외부 수정 충돌 처리가 부담), 병행(마크다운 원본 + SQLite 색인. 두 장점을 얻지만 동기화·색인 재구축 경로가 늘어남).
- 대가: 데이터를 다른 앱에서 바로 열 수 없다. 이식은 내보내기를 거쳐야 하며 내보내기 변환 품질(F-06)에 기댄다.
- 관련: Q-03, F-01, F-02.6, F-04, F-05, F-06, NF-01, NF-02, NF-03

### D-07 앱 셸: Tauri (조건부, 실패 시 Electron)
- 결정일: 2026-10-26 (사용자 결정, 카드 20261026-0014-NOTE-pm-p0-tech)
- 결정: 앱 셸은 Tauri로 하고 UI는 React로 만든다. 조건: 본 개발 전에 시험 빌드로 이 PC에서 무리 없이 빌드·실행되는지 먼저 확인한다. 안 되면 Electron으로 간다(그때는 새 D 번호로 기록). Rust·MSVC 빌드 도구는 사용자가 설치한다. (2026-10-26 보완: 시험 빌드 통과로 조건 충족, Tauri 유지 → D-12)
- 근거: Tauri는 시스템 WebView2를 써서 앱 용량과 실행 메모리가 작다(아이디어 노트 6절). 앱을 매일 켜 두므로 실행 메모리 부담이 크다. 이 PC는 RAM 16GB에서 개발 세션 여러 개가 함께 돈다(2026-10-26 확인 시점 여유 약 7.6GB). WebView2 런타임(155.0.4283.62)이 이미 설치되어 있다(2026-10-26 확인).
- 대안: Electron(Chromium을 내장해 실행 메모리·용량이 큼. Node/JS만으로 개발할 수 있고 자료가 가장 많음).
- 대가: Rust 툴체인과 MSVC가 필요하다. 첫 빌드가 무겁고 느려 병렬 세션과 메모리를 다툰다. 자료는 Electron보다 적다.
- 관련: Q-01, NF-01, NF-04, NF-05

### D-08 편집기 라이브러리: TipTap
- 결정일: 2026-10-26 (사용자 결정, 카드 20261026-0014-NOTE-pm-p0-tech. 기획 추천안은 BlockNote였으나 사용자가 TipTap을 골랐다)
- 결정: 블록 편집기는 TipTap(ProseMirror 기반)으로 만든다. 공개 npm의 MIT 패키지만 쓰고 유료(Pro·Cloud) 기능은 쓰지 않는다.
- 근거: 사용자 선택. TipTap은 유연하고 확장 자료가 많다. 2026-10-26 확인 결과, 필요한 확장(블록 손잡이, 제안 메뉴 기반 suggestion, 표, 코드, 이미지, 체크리스트, 마크다운)이 공개 npm에서 모두 MIT다(기능정의 "TipTap 확장 확인" 메모).
- 대안: BlockNote(Notion식 블록·/ 메뉴·블록 끌기 기본 제공, 틀 밖 변경이 어려움), Lexical(가볍지만 블록 UI·마크다운 변환을 더 직접 만들어야 함).
- 대가: 블록 손잡이·/ 메뉴·블록 이동 UI를 직접 만들어야 한다. TipTap 공식 / 메뉴는 패키지가 없는 실험 예제라(공식 문서 "This extension does not have a published package yet") 예제 코드를 가져와 직접 유지한다.
- 관련: Q-02, F-02, F-02.7, F-03, F-06

### D-09 AI 기능: 요약·다듬기·질의응답 모두 MVP
- 결정일: 2026-10-26 (사용자 결정, 카드 20261026-0014-NOTE-pm-p0-tech)
- 결정: F-08.1 선택 텍스트 요약, F-08.2 문장 다듬기·재작성, F-08.3 현재 노트 질의응답을 모두 MVP에 넣는다. F-08.4 태그 제안은 후순위로 둔다.

- 대안: 요약 → 다듬기 → 질의응답 순으로 나눠 넣기(기획 추천안: MVP는 요약·다듬기만).
- 대가: 질의응답은 노트 전체를 보내 입력 상한(2만 자)에 먼저 걸리고 비용이 가장 크며 대화 UI가 필요하다. 동작은 기능정의 F-08.3에 정했다.

### D-10 배포: 지금은 배포 안 함, MVP 뒤 재검토
- 결정일: 2026-10-26 (pm 결정, 카드 20261026-0014-NOTE-pm-p0-tech)
- 결정: D-03대로 지금은 배포하지 않는다. MVP가 끝난 뒤 다시 본다. API 키 접근 코드는 한 모듈로 모아, 배포하게 되면 그 모듈만 바꾸도록 한다.
- 근거: 아이디어 노트 2절(배포 계획 없음). 지금 MVP 동작은 배포 여부와 관계없다.
- 대안: 배포를 전제로 지금부터 키 구조 설계(사용자별 키 입력, 중계 서버 등).
- 대가: 배포를 하게 되면 키 처리 구조를 다시 설계해야 한다(아이디어 노트 7절).
- 관련: Q-05, D-03, NF-05

### D-11 MVP 범위·완료 기준 수치 확정
- 결정일: 2026-10-26 (사용자 결정, 카드 20261026-0015-NOTE-pm-p0-scope)
- 결정
  - 기획이 추가한 9개 기능(F-01.1 만들기, F-01.2 이름 바꾸기, F-01.3 삭제·휴지통·복원, F-01.4 트리 끌어 옮기기, F-02.6 이미지 저장 위치, F-02.7 블록 순서 이동, F-03 실행 취소, F-07 마지막 페이지 열기, F-08.6 API 키 등록)를 모두 MVP로 확정한다.
  - 기능정의 초안의 제안 수치를 모두 그대로 확정한다: 페이지 전환 1초, 자동 저장 디바운스 1초·최대 5초, 하루 AI 호출 50회, AI 입력 2만 자, 시작 3초, 검색 0.5초(페이지 1,000개·본문 약 1,000만 자), 입력 지연 기준 본문 5만 자, 유휴 메모리 300MB 이하, 검색 단축키 Ctrl+K, 블록 이동 단축키 Alt+↑/↓.
  - 조건: 구현 중 무리인 값이 나오면 pm이 사용자에게 다시 올린다. 바꾸면 새 D 번호로 기록한다.
- 근거: 사용자 선택. 추가 기능은 빠지면 앱이 성립하지 않거나(만들기·삭제·실행 취소 등) Notion식 블록 편집의 핵심(블록 이동, 아이디어 노트 3절)이다.
- 대안: 휴지통 없이 바로 삭제, 블록 이동·트리 끌기를 후순위로.
- 대가: MVP 구현량이 늘어난다. 특히 블록 이동은 D-08의 직접 구현 UI와 겹친다.
- 관련: F-01.1~F-01.4, F-02.6, F-02.7, F-03, F-07, F-08.6, NF-02, NF-04, F-08.5

### D-13 NF-04 메모리 판정 기준: Private 합계
- 결정일: 2026-10-26 (사용자 결정, 카드 20261026-0043-NOTE-pm-p0-5-result)
- 결정: NF-04의 유휴 메모리 300MB 이하는 앱 프로세스와 그 앱이 띄운 WebView2(msedgewebview2) 프로세스 전체의 Private 메모리 합계로 판정한다.
- 근거: Working Set 합계는 여러 프로세스가 함께 쓰는 공유 DLL 페이지를 프로세스마다 중복으로 센다. 빈 화면 측정에서 Working Set 합계 304.5~313.9MB, Private 합계 149.5~151.6MB였다(D-12).

- 대가: 판정 숫자가 작업 관리자 "메모리" 열 숫자보다 작게 나온다. TipTap·SQLite가 들어간 MVP에서 다시 잰다.
- 관련: NF-04, D-11, D-12
