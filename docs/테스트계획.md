## 0. 원칙

- 테스트 ID: `T-<요구 ID>-<번호>`. 요구 ID의 점은 뺀다(F-01.3 → `T-F013-01`). 보안 전용은 `T-CSP-`, `T-NAV-`, `T-AST-`, `T-SEC-`, 화면 공통 규칙은 `T-UI-`, 실제 백엔드에 붙여야만 확인되는 연결 항목은 `T-REAL-`(11.1절).
- 완료 기준 한 줄마다 테스트를 최소 1개 둔다. 기준에 없는 경계·실패 경우는 "(추가)"로 표시한다.
- 기능 판정은 디버그 빌드 설치본(1.2절 "기능 빌드")으로 한다. 성능(NF-04)·보안(F5·개발자 도구·환경 변수 무시)·데이터 폴더 위치(NF-01)는 릴리스 빌드로 판정한다. 개발 실행(`tauri dev`)은 CSP·devUrl·속도가 달라 판정에 쓰지 않는다.
- 시험용 코드 경로를 앱에 넣지 않는다(D-21). 실패 경우는 DB 잠금·파일 조작·네트워크 끊기처럼 앱 밖에서 만들고, 그래도 만들 수 없는 것(API 오류 종류 등)은 Rust 단위 테스트로 확인한다.
- 결함은 테스트 ID·재현 절차·기대·실제·증거 경로로 NOTE-pm에 `[결함]` 보고한다.
- 증거(화면 캡처·로그·측정 CSV)는 저장소 밖 `%USERPROFILE%\wy-note-qa\evidence\<날짜>\<테스트 ID>\`에 둔다. API 키·노트 실데이터가 찍힌 증거는 남기지 않는다.

## 1. 테스트 환경과 방법

### 1.1 방법 구분

| 표기 | 뜻 | 도구 |
|---|---|---|
| 수동 | 사람이 앱 화면을 조작하고 눈으로 판정 | 기능 빌드 또는 릴리스 빌드 앱, 화면 캡처 |
| 자동 | 실행 중인 앱의 WebView2에 원격 디버깅(CDP)으로 붙어 조작·관찰 | 앱 실행 전 환경 변수 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333`. QA 세션 전용 브라우저 자동화 도구로 `http://127.0.0.1:9333`에 붙는다. 순수 브라우저(vite만)는 가짜 백엔드(`src/api/mock.ts`)라 판정에 쓰지 않는다 |
| Rust | `src-tauri`의 `cargo test`(메모리 DB 또는 임시 파일 DB) | 계약-DB 10절·계약-AI의 단위 테스트 + 이 문서가 요청하는 항목 |
| 측정 | 시간·메모리·네트워크를 재서 수치로 판정 | PowerShell, 화면 녹화(Xbox Game Bar `Win+Alt+R`, 60fps 설정), CDP Performance, Python `sqlite3`(읽기 전용) |
| 코드 | 소스·설정 검색으로 확인 | Grep, `git log -p -S` |

- 원격 디버깅 포트는 성능 측정(시작 시간·메모리)에는 켜지 않는다. 포트가 켜진 상태의 수치는 참고로만 적는다.
- DB 확인은 Python `sqlite3`로 `file:<경로>?mode=ro` URI를 열어 읽기만 한다(앱 실행 중에도 WAL이라 안전). 쓰기는 테스트 데이터 준비와 일부러 잠금을 잡는 테스트(T-F05-07 등)에서만 한다.

### 1.2 빌드와 데이터 폴더 격리(D-22)

| 빌드 | 만드는 명령 | 쓰는 곳 |
|---|---|---|
| 기능 빌드 | `npm run tauri build -- --debug` → `src-tauri\target\debug\wy-note.exe`. 화면 묶음은 프로덕션(CSP 적용), Rust는 디버그(`WYNOTE_DATA_DIR`가 동작, 개발자 도구 열림) | 2~9절 기능 테스트, 11절 회귀 묶음, 자동(CDP) 테스트 대부분 |
| 릴리스 빌드 | `npm run tauri build` → `src-tauri\target\release\wy-note.exe`(설치본 포함) | NF-04 전체, T-NF01-01·02·05, T-NAV-04, T-SEC-06·09, T-UI-01 중 F5 부분 |

- 기능 빌드는 실행 전 `WYNOTE_DATA_DIR`를 저장소 밖 테스트 폴더(예 `%USERPROFILE%\wy-note-qa\data\<데이터 이름>`)로 준다. 빈 값은 무시되고 기본 폴더를 쓰므로 반드시 값을 넣는다. 릴리스 빌드는 이 변수를 읽는 코드가 아예 없다(`#[cfg(debug_assertions)]`, T-SEC-09).
- 이 변수로 격리되지 않는 것(테스트마다 염두에 둔다):
  - 창 크기·위치 파일(window-state 플러그인, `%APPDATA%\com.wynote.desktop`)
  - WebView2 데이터(`%LOCALAPPDATA%\com.wynote.desktop`)
  - 한 번만 실행(single-instance): 실제 앱이 켜져 있으면 테스트 앱이 뜨지 않고 실제 앱이 앞으로 온다. 테스트 전에 실제 앱이 꺼졌는지 확인한다.
  - "폴더 열기": opener 범위가 `$APPDATA`라 바꾼 폴더는 열리지 않는다. 그래서 T-NF01-02는 릴리스 빌드로만 판정한다.
- 릴리스 빌드는 실제 데이터 폴더 `%APPDATA%\com.wynote.desktop`를 쓴다. 지금은 사용자 데이터가 없다(v1 개발 DB는 D-29에 따라 지웠다). 릴리스 테스트(NF-04·NF-01·보안)는 사용자가 실사용을 시작하기 전에 끝낸다. 실사용 뒤 다시 필요하면 사용자에게 먼저 묻는다(D-30 ③).
- 테스트 API 키는 저장소 밖에만 둔다. 실제 Claude API 호출은 1.4절 예산 안에서, 실행할 때마다 NOTE-pm 승인을 받는다.

D2 생성 규칙
- 난수는 시드 고정 LCG(`x = (1103515245x + 12345) mod 2^31`, 시드 20261026)로 만들어 같은 데이터를 다시 만들 수 있게 한다.
- 트리: 최상위 20개, 단계마다 자식 0~8개, 최대 깊이 5. 정확히 1,000개가 되면 멈춘다.
- 크기: D3 1개(5만 자) + 나머지 999개는 평균 약 9,960자(2,000~20,000자 균등 분포에서 뽑고, 합계가 10,000,000 ± 1%가 되게 마지막에 맞춤).
- 글: 한글 낱말 약 2,000개 목록(저장소 밖 파일) 80% + 영어 낱말 15% + 숫자 5%. 문단 200~600자, 문단 10개마다 제목 블록, 페이지마다 목록·체크리스트·코드·표 중 1~2개.
- 찾을 낱말 심기(정답 개수를 알기 위해): `회의록`은 정확히 37개 페이지에, `의록에`(어절 중간)는 5개 페이지에, 고유 표식 `QAZ0001`~`QAZ1000`은 페이지마다 하나씩(페이지 끝 문단), 2글자 `결재`는 300개 페이지에, 한 글자 `뷁`은 3개 페이지에. `없는검색어`는 어디에도 넣지 않는다(전체 훑기 최악 경우).
- 만든 뒤 확인: `select count(*) from pages` = 1000, `select sum(length(body)) from page_fts` ≈ 1,000만, `QAZ0500` 검색 1건, `PRAGMA user_version` = 2.

메모리 합계 스크립트(PowerShell, 앱 프로세스와 그 자손 전체)
```powershell
$all = Get-CimInstance Win32_Process
$root = $all | Where-Object { $_.Name -eq 'wy-note.exe' }
$ids = @($root.ProcessId); $i = 0
while ($i -lt $ids.Count) { $ids += ($all | Where-Object { $_.ParentProcessId -eq $ids[$i] }).ProcessId; $i++ }
$procs = Get-Process -Id $ids -ErrorAction SilentlyContinue
"{0} procs, Private {1:N1} MB, WorkingSet {2:N1} MB" -f $procs.Count, (($procs | Measure-Object PrivateMemorySize64 -Sum).Sum/1MB), (($procs | Measure-Object WorkingSet64 -Sum).Sum/1MB)
```

### 14.2 새로 생긴 확인 사항

P3-8 판에서 생긴 1~4 중 1~3은 D-30으로 정해졌다. 5·6은 이번 판(D-30~D-33 반영)에서 생겼고 pm 결정(둘 다 A)으로 닫았다. 프론트 수정은 P3-10, 기능정의 F-08.1·F-08.5 개정은 planner가 나중에 한다.

1. **릴리스 빌드 테스트의 데이터 폴더** → 결정 D-30 ③: 실사용 시작 전에 릴리스 테스트(NF-04·NF-01·보안)를 끝낸다. 실사용 뒤 다시 필요하면 사용자에게 먼저 묻는다. (1.2절, NF-04 공통, T-NF01-01·02·05, T-SEC-09)
2. **키 확인 호출을 30회에 넣는지** → 결정 D-30 ④: 30회는 크레딧을 쓰는 메시지 호출만 센다. `GET /v1/models` 키 확인은 따로 10회 이내. (1.4절)
3. **요약 결과의 버튼** → 결정 D-30 ⑤: 요약에도 `삽입`·`복사`, `바꾸기`는 다듬기에만. (T-F08-04, T-F081-03)
4. **"랜은 붙었지만 인터넷 없음"의 실기 확인**: 방화벽 규칙으로 만들려면 관리자 권한이 필요해 QA 세션에서 할 수 없다. Rust 단위(연결 실패 → `Offline`, 횟수 안 셈)로만 확인한다. 실기 확인이 필요하면 사용자가 직접 해야 한다. (T-F08-02)
5. **잘림(`max_tokens`) 결과의 `삽입`** → pm 결정 A: 잘림도 정상 완료가 아니다. 요약·다듬기·질의응답 세 탭 모두 `삽입`·`바꾸기`를 끄고 `복사`만 남긴다. 결정 전 배경: pm 결정(D-31 적용)은 "정상 완료가 아니면 세 탭 모두 `삽입`·`바꾸기`를 끄고 `복사`만"이고 D-31은 잘림도 정상 완료가 아니라고 한다. 그런데 기능정의 F-08.5는 잘림에 "바꾸기를 끈다"만 적었고, 지금 코드(`3bc7695`)는 잘림일 때 요약·다듬기의 `삽입`과 질의응답 답의 `삽입`을 켜 둔다(`src/ai/AiPanel.tsx`: `incomplete`만 보고 `truncated`는 `바꾸기`에서만 본다. `aiLogic.ts` `incompleteReason`은 `max_tokens`를 null로 돌려준다). 추천: 잘림도 세 탭 모두 `삽입`을 끈다(pm 결정 문구 그대로). (T-F08-08)
6. **요약 `삽입`의 위치** → pm 결정 A: F-08.1대로 커서 위치, 세 탭 같은 규칙. 선택이 있으면 덮어쓰지 않고 선택 끝 바로 뒤, 선택이 없으면 커서 위치, 커서를 한 번도 둔 적이 없으면 요청 범위 아래. 결정 전 배경: F-08.1은 "삽입(커서 위치에 넣기)"인데, 지금 코드의 요약 `삽입`은 요청 범위의 마지막 블록 바로 아래에 넣고(`editorTarget.ts` `insertBelow`), 범위가 바뀐 경우에만 커서 자리에 넣는다. 질의응답 답의 `삽입`은 커서 위치다. 추천: 기능정의대로 커서 위치(사용자가 위치를 고를 수 있음). 요청 범위 아래가 낫다고 보면 기능정의·화면설계 문구를 고친다. (T-F081-03)
